# worker-oidc login/signup/consent pages as a React SPA

## Context

`worker-oidc`'s `/login`, `/signup`, and `/consent` pages (`src/pages.ts`) are plain hand-written HTML strings with inline `<script>` tags, served by the Hono app itself (`registerOidcPages`). They work, but they're awkward to extend — no component reuse, no templating, manual `escapeHtml` calls for anything user-supplied, no build step.

The rest of this monorepo already has an established pattern for exactly this situation — a Cloudflare Worker that needs both real server-side logic (bindings, auth) and a rich browser UI — in `apps/worker-client`: a Vite + React + TanStack Router SPA served as static assets, with a thin Worker (`worker/index.ts`) handling only specific API path prefixes via `assets.run_worker_first`. `apps/worker-admin` (converted in the prior `worker-admin-oidc-client` change) uses the same toolchain, minus the Worker half (it's pure static assets, no backend logic of its own).

`worker-oidc` needs the hybrid shape: it keeps real backend logic (D1, Better Auth, the OAuth provider plugin, the client-bootstrap route), but its three pages become React components built and served as static assets.

## Goals

- `/login`, `/signup`, `/consent` become React components under `src/routes/`, built with Vite and routed with TanStack Router, matching `worker-admin`'s file-per-route shape.
- Each page keeps calling the same Better Auth HTTP endpoints its current inline `<script>` already calls (`sign-in/email`, `sign-up/email`, `oauth2/authorize`, `oauth2/continue`, `oauth2/consent`) — no behavior change to the flow itself, only how the UI is built.
- `/login` and `/signup` additionally fetch the requesting OAuth client's public name via `POST /api/auth/oauth2/public-client-prelogin` (a genuinely public, no-session-required endpoint the `oauthProvider` plugin ships for exactly this purpose) so they can show "Sign in to continue to `<client name>`" instead of a bare form — `/consent` already does an equivalent lookup today and keeps doing so, just client-side now via the same endpoint instead of `auth.api.getOAuthClientPublic` called server-side in the Hono route.
- The Worker keeps handling `/api/auth/*` (Better Auth's handler) and `/internal/*` (the bootstrap route) exactly as today; everything else is served as the built SPA, via `assets.run_worker_first: ["/api/auth/*", "/internal/*"]` and `not_found_handling: "single-page-application"` — the same `wrangler.jsonc` shape `worker-client` uses.

## Non-goals

- No new server-side data endpoint. `/oauth2/public-client-prelogin` already covers what the pages need; nothing is added to the Worker to support this.
- No automated component/route tests for the new pages. This repo has no frontend component test runner (`worker-admin`'s `login.tsx`/`auth-callback.tsx` already carry zero automated tests, by established precedent) — a manual browser check covers this instead, same as the prior spec's approach.
- No visual redesign beyond what converting to React naturally implies (form structure, error text, and behavior stay the same as today's pages). Styling polish is left for later.
- No change to `worker-admin`'s own code, the OAuth client-bootstrap route's behavior, or `@capstone/auth-verify`.

## Architecture

### Directory restructuring

`worker-client` is the only existing precedent for "Worker + React SPA in one deployable": backend Worker code lives in `worker/`, browser code lives in `src/`. `worker-oidc` currently has all its backend code under `src/` (no browser code exists yet), so adding React means inverting that:

- **Moved, unchanged in content:** `src/index.ts`, `src/auth.ts`, `src/db/*`, `src/register-worker-admin-client.ts` → `worker/index.ts`, `worker/auth.ts`, `worker/db/*`, `worker/register-worker-admin-client.ts`.
- **Deleted:** `src/pages.ts` (`registerOidcPages`) and its call site in `worker/index.ts` (formerly `src/index.ts`) — page-serving is no longer the Worker's job.
- **New:** `src/main.tsx`, `src/routes/__root.tsx`, `src/routes/index.tsx`, `src/routes/login.tsx`, `src/routes/signup.tsx`, `src/routes/consent.tsx`, `src/routeTree.gen.ts` (generated by the TanStack Router Vite plugin, `autoCodeSplitting: true`), `index.html` — all mirroring `worker-admin`'s equivalent files.
- **Path updates:** every existing reference to `./src/...` or `../src/...` moves to `./worker/...` / `../worker/...`: `auth.cli.ts`, `drizzle.config.ts` (its `schema` path), and all four files under `test/` (`register-worker-admin-client.test.ts`, `helpers/call-app.ts`, plus the two that only reference `../../src/index` for the app import).

### Pages

- **`src/routes/login.tsx`** — on mount, `POST /api/auth/oauth2/public-client-prelogin` with `{ client_id, oauth_query }` parsed from the route's search params, to render the requesting client's name (falling back to a generic "Sign in" heading if the client_id is missing/unrecognized — mirrors today's `catch(() => null)` fallback behavior). Email/password form submits to `POST /api/auth/sign-in/email`; on success, `window.location.href = '/api/auth/oauth2/authorize' + window.location.search` (same resume mechanism as today). On failure, renders an inline error, same as today's `#error` paragraph.
- **`src/routes/signup.tsx`** — same prelogin client-name fetch. Form submits to `POST /api/auth/sign-up/email`, then `POST /api/auth/oauth2/continue` with `{ created: true, oauth_query }`, then navigates to the `url` the response returns. Same error-handling shape as today.
- **`src/routes/consent.tsx`** — same prelogin fetch for client name (replacing today's server-side `auth.api.getOAuthClientPublic` call) plus the `scope` query param for the "Requested access" line. Allow/Deny buttons `POST /api/auth/oauth2/consent` with `{ accept, oauth_query }`, then navigate to the returned `url`. Same error-handling shape as today.
- **`src/routes/index.tsx`** — trivial placeholder page (this worker isn't meant to be browsed at its bare root by a real user in normal operation).

All three form pages read their OAuth query-string parameters via TanStack Router's search-param handling rather than `window.location.search` directly, but resume/redirect navigations (`window.location.href = ...`) stay as real browser navigations, not router pushes — the destinations are Better Auth API routes and (via the OAuth flow) eventually another origin entirely (`worker-admin`'s `/auth-callback`), not in-app routes.

XSS-escaping (today's hand-rolled `escapeHtml` for the consent page's client name) is no longer a separate concern — JSX escapes interpolated text by default, so a malicious/unrecognized `client_id` reflected into the page can't inject markup, structurally rather than by a dedicated helper.

### `wrangler.jsonc`

Keeps `main: "worker/index.ts"`, `d1_databases`, `observability`, `upload_source_maps`, and the existing `dev.port`/`dev.inspector_port` block (still used by the Cloudflare Vite plugin to run the Worker half via Miniflare). Adds:

```jsonc
"assets": {
    "not_found_handling": "single-page-application",
    "run_worker_first": ["/api/auth/*", "/internal/*"]
}
```

Same shape as `worker-client`'s `wrangler.jsonc`. Everything outside those two prefixes is served from the Vite build output as the SPA.

### `package.json` / tooling

- `dev` changes from `"wrangler dev"` to `"vite"` — the Cloudflare Vite plugin runs the real Worker (D1 binding included) inside the same dev process via Miniflare, the same mechanism `wrangler dev` itself uses, just orchestrated through Vite (this is Cloudflare's documented supported pattern for combining bindings with a Vite-built frontend, and is exactly what `worker-client` already does in this repo).
- Adds `build: "tsc -b && vite build"` and `preview: "npm run build && vite preview"`.
- New deps, matching `worker-admin`/`worker-client`: `react`, `react-dom`, `@tanstack/react-router`, `@tanstack/react-router-devtools` (dependencies); `@cloudflare/vite-plugin`, `@tanstack/router-plugin`, `@vitejs/plugin-react`, `vite`, `@types/react`, `@types/react-dom` (devDependencies).
- `test`, `test:run`, `typegen`, `migrations:auth`, `lint` stay as they are today. `deploy` changes from `"wrangler deploy"` to `"npm run build && wrangler deploy"`, matching `worker-admin`/`worker-client` — the Vite build has to run first to produce the static assets `wrangler deploy` picks up.

### `tsconfig.json`

Becomes a references-only shell over three project configs, matching `worker-client` exactly:

- `tsconfig.app.json` — extends `@capstone/typescript/configs/tsconfig.app.json`, `include: ["src"]`.
- `tsconfig.node.json` — extends `@capstone/typescript/configs/tsconfig.node.json`, `include: ["vite.config.ts"]`.
- `tsconfig.worker.json` — extends `@capstone/typescript/configs/tsconfig.node.json` (matching today's single config's base, since this is Worker/Node code, not browser code), `types: ["./worker-configuration.d.ts", "vite/client"]`, `include: ["worker"]`.

`test/tsconfig.json` keeps its current shape, just repoints its `../worker-configuration.d.ts` include (unaffected — that file lives at the app root, not under `src`/`worker`) and continues to extend the root `tsconfig.json`.

### Dev port

The Vite dev server needs its own port, separate from the Worker's `dev.port`/`inspector_port` in `wrangler.jsonc` (which the Vite plugin still uses internally for the Miniflare-run Worker half) — same two-port split `worker-admin` and `worker-client` already have. Exact port numbers picked during implementation to avoid colliding with the other four workers' dev/inspector ports; the collision-avoidance comments in all affected `wrangler.jsonc`/`vite.config.ts` files get updated together.

## Testing / verification

- `test/pages.test.ts` is deleted, no replacement — matches the `worker-admin`/`worker-client` precedent of no automated tests for route components.
- `test/cors.test.ts`, `test/register-worker-admin-client.test.ts` — unchanged in logic, updated only for the `src/` → `worker/` import path change.
- `test/oauth-client-flow.test.ts` — unchanged. It only ever exercised `/api/auth/*` routes directly and asserted on redirect `Location` header paths (`/login`, `/consent`); it never actually rendered or fetched those page routes as HTML, so removing their Hono handlers doesn't affect it.
- **Manual browser check:** sign up a new account via `/signup`, confirm the client name renders correctly (sourced from `oauth2/public-client-prelogin`), sign in via `/login`, see and accept `/consent`, land back on `worker-admin` showing "signed in as `<email>`". Same gap already flagged as outstanding from the prior `worker-admin-oidc-client` PR, now also covering these pages' new implementation.

## Versioning

`npm run changeset`, selecting `@capstone/openid-connect` only (minor bump) — this change doesn't touch `worker-admin` or `@capstone/auth-verify`.

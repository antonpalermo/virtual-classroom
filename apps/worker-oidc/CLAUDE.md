# CLAUDE.md — worker-oidc

`@capstone/openid-connect` — email/password sign-in backed by D1 via Drizzle, plus Better Auth's `oauthProvider` plugin (from `@better-auth/oauth-provider`) so this worker serves a real OIDC provider (`/.well-known/openid-configuration`, `/api/auth/oauth2/{authorize,token,userinfo,introspect,revoke,end-session}`, `/api/auth/jwks`). `apps/worker-admin` is registered as a public, PKCE-required, native-app OAuth client (via the bootstrap route below) and drives the full Authorization Code + PKCE flow against this worker — see `apps/worker-admin/CLAUDE.md` for the client side.

This worker follows `apps/worker-client`'s split: a real backend Cloudflare Worker under `worker/` (handling only `/api/auth/*`, `/internal/*`, `/api/admin/*`, and `/api/invites/*` — see "Routing split" below) plus a Vite + React + TanStack Router SPA under `src/` for everything else, built as static assets. There is no more `src/pages.ts` — the old hand-written HTML+JS `/login`/`/consent` pages have been replaced by real React route components (`src/routes/login.tsx`, `consent.tsx`, `accept-invite.tsx`).

**There is still no *self-service* sign-up.** No `/signup` route, no reachable `/sign-up/email` endpoint, and Google sign-in can't create a new account either (see `worker/auth.ts`'s `disabledPaths` and `socialProviders.google.disableSignUp` below). What now exists instead: an admin, signed into `apps/worker-admin`'s `/users` dashboard, creates a user via `POST /api/admin/users` (`worker/admin-users.ts`) and hands the returned one-time invite link to them out of band; the invitee sets their own password by visiting it (`src/routes/accept-invite.tsx` → `POST /api/invites/accept`, `worker/accept-invite.ts`) — see "Admin user management" below. `worker/bootstrap-admin-user.ts`'s curl-only bootstrap route is still how the *very first* admin account gets seeded (there's no admin yet to drive the dashboard until then).

## Routing split

`wrangler.jsonc`'s `assets` block is what makes this work:

```jsonc
"assets": {
    "not_found_handling": "single-page-application",
    "run_worker_first": ["/api/auth/*", "/internal/*", "/api/admin/*", "/api/invites/*"]
}
```

`run_worker_first` sends only those four prefixes to the Worker (`worker/index.ts`); every other request — including `/login`, `/consent`, `/accept-invite`, and any path that doesn't match a built asset — is served from the built SPA in `dist/`, with `not_found_handling: single-page-application` falling back to `index.html` (the SPA shell) for unmatched paths so the client-side router can take over. There's no server-side route matching for the page paths — they exist only as TanStack Router file routes on the client.

## Layout

### `worker/` — the backend Worker

- `worker/index.ts` — Hono app. Registers the bootstrap route (`registerBootstrapRoute`, see below), the admin-users routes, and the accept-invite route, opens CORS on `/api/admin/*` and on three endpoints called directly cross-origin from `worker-admin`'s and `worker-client`'s browser JS (`/api/auth/jwks`, `/api/auth/oauth2/userinfo`, `/api/auth/oauth2/token` — none of them cookie-gated, same reasoning `worker-auth` applies to its own `/api/auth/jwks`), and mounts Better Auth's handler at `/api/auth/*` unmodified for everything else. No longer serves any HTML pages itself.
- `worker/auth.ts` — `createAuth(db, env)`, the Better Auth factory: Drizzle/D1 adapter, `emailAndPassword` enabled, a Google `socialProviders` entry (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`), `jwt()` + `oauthProvider({ loginPage: '/login', consentPage: '/consent', allowPublicClientPrelogin: true })` plugins. `jwt()` is a hard dependency of `oauthProvider` (it signs OIDC `id_token`s; omitting it throws `BetterAuthError("jwt_config")` at request time), not an optional pairing. `loginPage`/`consentPage` point at the SPA routes described below (asset-served, not Worker routes) — there's no `signup` option anymore; `prompt=create` (unused by any current client) falls back to `loginPage`. `allowPublicClientPrelogin: true` is a hard prerequisite for `src/routes/{login,consent}.tsx`'s client-name lookups (`POST /api/auth/oauth2/public-client-prelogin`) to work at all — without it the endpoint unconditionally 400s and the pages silently fall back to showing the raw `client_id`. `trustedOrigins` includes `env.BETTER_AUTH_URL` (redundant — Better Auth already auto-trusts its own configured `baseURL` origin) and, notably, `'https://example.com'`, needed so the test suite's synthetic cross-origin requests (the `/oauth2/consent` POST in particular, which carries both a session cookie and an `Origin` header) pass `originCheckMiddleware`. Built as a factory rather than a module-level singleton because the D1 binding only exists inside a request's `env`. No self-service accounts: `disabledPaths: ['/sign-up/email']` 404s that route for any HTTP caller (it only gates the router — see `node_modules/better-auth/dist/api/index.mjs`'s `onRequest` — so `auth.api.signUpEmail`, called internally by `worker/bootstrap-admin-user.ts`, still works; Better Auth's own `emailAndPassword.disableSignUp` flag would block that internal call too, since it's checked inside the endpoint handler itself), and `socialProviders.google.disableSignUp: true` stops a first-time Google sign-in from creating a user (it redirects back with `?error=signup_disabled` instead — see `src/GoogleButton.tsx`). Also declares `user.additionalFields` for `role`/`banned`/`banReason`/`banExpires` — better-auth's drizzle adapter only selects/writes columns it's told about, so without this the columns (real, in `worker/db/schema.ts`) silently read as `undefined` through any better-auth API even though they exist in D1; each is `input: false` (same shape as the `admin` plugin's own schema, `node_modules/better-auth/dist/plugins/admin/schema.mjs`) so they're not settable through any public-input-validated endpoint — only `worker/admin-users.ts`'s own direct Drizzle writes change them. `databaseHooks.session.create.before` rejects sign-in for a `banned` user (`APIError.from('FORBIDDEN', { code: 'BANNED_USER' })`) — the same mechanism the `admin` plugin uses internally for this, hand-added since that plugin isn't enabled here (see "Admin user management" below) — and auto-lifts a ban whose `banExpires` has passed instead of erroring. `customIdTokenClaims` also adds `role` (falling back to `'user'`) alongside `email`, populating the previously-dormant `role?: string` field in `@capstone/auth-verify`'s `AccessTokenClaims`.
- `worker/register-oauth-client.ts` — `registerBootstrapRoute(app)`, mounts `POST /internal/oauth-clients/:name`, where `:name` must be one of `CLIENT_NAMES` (`worker-admin`, `worker-client`; 404 otherwise). Gated by a `Bearer <BETTER_AUTH_SECRET>` header (401 otherwise) and a required `redirect_uri` query param (400 otherwise). Idempotent: looks up an existing `oauth_client` row with that name first and returns its `client_id` if found; otherwise it synthesizes a throwaway session directly on the shared `AuthContext` (there's no real signed-in user in this bootstrap flow, but the plugin's `adminCreateOAuthClient` unconditionally requires a session) against a fixed upserted "bootstrap" user row, then calls `adminCreateOAuthClient` to create a public client (`token_endpoint_auth_method: 'none'`, `application_type: 'native'` — required so loopback `http://localhost:...` redirect URIs validate, `skip_consent: false`, `grant_types: ['authorization_code']`). A concurrent duplicate insert (caught via `oauthClient.name`'s unique index) is treated as a race loss, not an error — the loser re-reads and returns the winner's `client_id`. Called once per environment via a manual curl (see below), never by a client itself.
- `worker/admin-users.ts` — `registerAdminUsersRoutes(app)`, mounts `GET /api/admin/users`, `POST /api/admin/users`, `PATCH /api/admin/users/:id`, `POST /api/admin/users/:id/{ban,unban}`, `DELETE /api/admin/users/:id`. Every route runs a shared `requireAdmin` gate: extract the `Authorization: Bearer <id_token>` header, verify it **in-process** against this worker's own signing keys via `@capstone/auth-verify`'s `verifyAccessTokenWithJwks` (fed the JSON straight from calling `auth.handler()` on this worker's own `/api/auth/jwks` route — deliberately not a real self-`fetch()`; it already holds its own keys, so a network round trip back to itself would be pure overhead, and in the Vitest/Miniflare sandbox a real self-fetch isn't guaranteed to land on the same D1 instance the request is using), then re-look-up the token's `sub` fresh in D1 and require `role === 'admin' && !banned` — never trusting the token's own `role` claim, so a demotion or ban takes effect on the next call rather than waiting for the token to expire. `POST /api/admin/users` doesn't take a password: it creates the user via `authContext.internalAdapter.createUser(..., { method: 'admin' })` with no credential account, generates a random invite token (`generateRandomString` from `better-auth/crypto`, 7-day expiry, stored in the new `invite` table), and returns `{ user, inviteUrl }` for the admin to copy/hand off (see "Admin user management" below). Role/ban/delete on **your own** account all 400 (self-lockout guard). Also exports `setUserPassword(db, env, userId, newPassword)`, shared with `worker/accept-invite.ts`: hashes via `authContext.password.hash`, then either `updatePassword` (an existing credential account — checked via `findCredentialAccount`) or `createAccount` (a brand-new one, `providerId: 'credential'`, `issuer: createLocalAccountIssuer('credential')` from `@better-auth/core/db`) — mirrors the `admin` plugin's own `setUserPassword` endpoint (`node_modules/better-auth/dist/plugins/admin/routes.mjs`) exactly, since its own public API (`auth.api.setPassword`) requires a real cookie-backed session an anonymous invitee doesn't have.
- `worker/accept-invite.ts` — `registerAcceptInviteRoute(app)`, mounts `POST /api/invites/accept` (deliberately **not** under `/internal/*` — that prefix's convention here is "trusted, `BETTER_AUTH_SECRET`-gated"; this is anonymous and gated by the invite token itself). Body `{ token, password }`: 404 if the token doesn't match an `invite` row, 400 if already used or past `expiresAt`, 400 if the password fails `authContext.password.config.{min,max}PasswordLength`. On success: `setUserPassword` (above), marks the user `emailVerified: true` (proves control of the invite link/email, same rationale as `worker/bootstrap-admin-user.ts`), marks the invite row `usedAt`.
- `worker/bootstrap-admin-user.ts` — `registerBootstrapAdminUserRoute(app)`, mounts `POST /internal/users/bootstrap-admin`, the only way left to create an account. Gated the same way as the client bootstrap route above (`Bearer <BETTER_AUTH_SECRET>`, 401 otherwise; 400 if `email`/`password` aren't both non-empty strings in the JSON body). Calls `auth.api.signUpEmail` directly (not the HTTP `/sign-up/email` route), so `disabledPaths` above never sees it, then updates the created row to `emailVerified: true` directly via Drizzle — `signUpEmail` always creates `emailVerified: false` and nothing else in this worker ever verifies an email, so without this a bootstrapped account could never link a later Google sign-in (Better Auth's account linking defaults to `requireLocalEmailVerified: true`); bootstrap is already `BETTER_AUTH_SECRET`-gated, i.e. already trusted, so marking it verified directly is safe. Idempotent: a duplicate email throws Better Auth's `UNPROCESSABLE_ENTITY`/`USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL` (checked via `error.body.code`, not just `error.status`, since `FAILED_TO_CREATE_USER` throws the same status for a genuine failure), which is caught and turned into a 200 `{ created: false, ... }` no-op — a re-run does **not** update the existing user's password or name. `name` defaults to `'Admin'` if omitted. Run it once per environment:

    ```bash
    curl -X POST "http://localhost:8791/internal/users/bootstrap-admin" \
        -H "Authorization: Bearer <this worker's BETTER_AUTH_SECRET>" \
        -H "Content-Type: application/json" \
        -d '{"email":"<admin email>","password":"<admin password>","name":"Admin"}'
    ```
- `worker/db/client.ts` — `createDb(d1)`, wraps the `OIDC_DB` binding in a Drizzle client.
- `worker/db/schema.ts` — **generated** by `npx auth@latest generate` (see `auth.cli.ts` below), then owned/hand-edited from there. Don't hand-author from scratch; regenerate after adding/changing plugins. `user.role`/`banned`/`banReason`/`banExpires` and the whole `invite` table are hand-added, *not* part of the generated shape — they're the `admin` plugin's own field set (see `worker/auth.ts` above), added by hand because this worker deliberately doesn't enable that plugin, so regenerating is expected to produce **no diff** for them (confirmed by actually running the regen command and diffing before adding these — it doesn't reproduce this shape on its own; don't assume a future regen will either).
- `auth.cli.ts` (repo root of this workspace) — Node-only shim used solely by the Better Auth CLI to generate `worker/db/schema.ts` (the CLI can't see a real D1 binding). Never imported by the Worker itself.
- `drizzle.config.ts` / `drizzle/*.sql` — `drizzle-kit`-generated migrations (schema source `./worker/db/schema.ts`), applied via `wrangler d1 migrations apply OIDC_DB` (uses the `migrations_dir` set in `wrangler.jsonc`).
- `worker-configuration.d.ts` — **generated** by `wrangler types`; don't Read it in full — `grep` for the specific binding/type you need. Note `wrangler types` also picks up keys from a local `.dev.vars` file (not `.dev.vars.example`) to type `BETTER_AUTH_SECRET`/`BETTER_AUTH_URL`/`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` on `Env` — an untyped `env.BETTER_AUTH_*` reference usually means `.dev.vars` is missing locally.

### `src/` — the React SPA

- `src/main.tsx` — entry point; creates the TanStack Router instance from the generated route tree and renders `<RouterProvider>` into `#root`.
- `src/GoogleButton.tsx` — "Continue with Google" button, rendered by `login.tsx`. `POST`s `/api/auth/sign-in/social` with `provider: 'google'`, `callbackURL: '/api/auth/oauth2/authorize?<oauth_query>'`, `errorCallbackURL: '<current page>?<oauth_query>'`, and the signed `oauth_query` itself, then redirects the browser to the returned `url`. Sending `oauth_query` (not just `callbackURL`) lets the oauth-provider plugin track the flow, so `prompt=login`/`max_age` are honored instead of looping back to `/login`. After Google's callback Better Auth sets the session cookie and lands on `authorize`, resuming the flow like the email sign-in does. A failed Google leg (cancelled consent, `account_not_linked`, or `signup_disabled` — no existing user for this Google account, since `socialProviders.google.disableSignUp: true` in `worker/auth.ts` blocks creating one) returns to the same page with `?error=<code>`, which the button shows as a message (`error`/`error_description` are stripped before the query is reused, so they never reach the signed `oauth_query`). The button disables itself while the request is in flight and shows an error if the request fails.
- `src/routes/__root.tsx` — root layout: bare `Outlet` + `TanStackRouterDevtools`.
- `src/routes/index.tsx` — placeholder index route (`worker-oidc — OpenID Connect provider.`).
- `src/routes/login.tsx` — the sign-in page, and the only account-entry page left. On mount, if the URL has a `client_id` query param, it `POST`s `/api/auth/oauth2/public-client-prelogin` (body `{ client_id, oauth_query }`, where `oauth_query` is the raw query string) to look up and display the requesting client's `client_name`. On submit, it `POST`s email/password to `/api/auth/sign-in/email`, then on success redirects the browser to `/api/auth/oauth2/authorize?<oauth_query>` to resume the OAuth flow. No sign-up link — there's nothing to link to.
- `src/routes/consent.tsx` — the consent page. Reads `client_id`/`scope` off the query string, seeds the displayed client name with the raw `client_id` and upgrades it via the same `public-client-prelogin` lookup once it resolves. "Allow"/"Deny" both `POST` `/api/auth/oauth2/consent` (body `{ accept, oauth_query }`) and redirect the browser to the `url` in the JSON response.
- `src/routes/accept-invite.tsx` — the invite-redemption page (the other account-entry path, alongside `login.tsx` — see "Admin user management" below). Reads `?token=` off the query string; a password + confirm form `POST`s `{ token, password }` to `/api/invites/accept` (same-origin, no CORS needed), then shows a "sign in" link on success or an inline error (invalid/expired/already-used token, password too short) on failure.
- `src/routeTree.gen.ts` — **generated** by the TanStack Router Vite plugin (`autoCodeSplitting: true`) from `src/routes/`. Don't hand-edit; let the dev server regenerate it.

All three pages talk to `/api/*` with same-origin `fetch` (no CORS needed — they're served from the same origin as the Worker) and drive their flow entirely client-side; none is server-rendered.

## Regenerating the schema after a config change

`auth@latest` can resolve to a version bundling a newer, schema-incompatible `@better-auth/core` than this workspace's pinned `better-auth@^1.7.1` — pin the CLI version to match and review the generated diff (`git diff worker/db/schema.ts`, expecting only additive changes) before running `drizzle-kit generate`.

```bash
npx auth@1.7.1 generate --config ./auth.cli.ts --adapter drizzle --dialect sqlite --output worker/db/schema.ts -y
npx drizzle-kit generate
```

## Admin user management

`apps/worker-admin`'s `/users` dashboard (see `apps/worker-admin/CLAUDE.md`) manages every user in this worker's D1 — the single identity store shared by `worker-client` and `worker-admin` — through the REST API in `worker/admin-users.ts` (`GET`/`POST /api/admin/users`, `PATCH`/`DELETE /api/admin/users/:id`, `POST /api/admin/users/:id/{ban,unban}`) plus the invite-redemption endpoint in `worker/accept-invite.ts` (`POST /api/invites/accept`). Two roles only (`user`/`admin`, no manager tier); CRUD + ban/unban, no impersonation, no audit log, no pagination — see the field-level detail in the `worker/` bullets above and `docs/superpowers/specs/2026-09-14-admin-user-roles-dashboard-design.md` for the older, superseded three-tier design this deliberately doesn't reuse (its own research is why this worker hand-rolls the API instead of enabling the `admin` plugin — that plugin's routes only authenticate via bearer-session tokens, which don't interoperate with the OAuth-provider access tokens/id_tokens this worker actually issues).

`.dev.vars.example` lists the required local vars (`BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`); copy it to `.dev.vars` (gitignored) and fill in a real secret before running `dev`. Run `npm run migrations:auth` before first use. Deployed, the Google pair is set with `wrangler secret put`.

Google sign-in needs a Google Cloud OAuth client whose authorized redirect URI is `<BETTER_AUTH_URL>/api/auth/callback/google` (`http://localhost:8791/api/auth/callback/google` locally) — sign-in fails with `redirect_uri_mismatch` otherwise. With the vars unset the button shows an error on click. Account linking is left at Better Auth's defaults, which require the *local* account's email to be verified before a Google sign-in can link to it — `worker/bootstrap-admin-user.ts` marks every account it creates `emailVerified: true` specifically so this isn't a dead end (there's no other path to an account, and no separate email-verification flow anywhere in this worker). Don't set `requireLocalEmailVerified: false` instead: an attacker could pre-register a victim's email through some other path and the victim's later Google sign-in would then link into the attacker's account. A real round trip through Google's consent screen is a manual check only.

## Connecting a client

`apps/worker-admin` and `apps/worker-client` are the two clients today, each connected via the bootstrap route (`worker/register-oauth-client.ts`) plus the same Authorization Code + PKCE flow — see `apps/worker-admin/CLAUDE.md` for the full step-by-step. In short: bootstrap each once per environment with (swap `worker-admin`/`8790` for `worker-client`/`5173` for the other)

```bash
curl -X POST "http://localhost:8791/internal/oauth-clients/worker-admin?redirect_uri=http://localhost:8790/auth-callback" \
    -H "Authorization: Bearer <this worker's BETTER_AUTH_SECRET>"
```

which returns `{"client_id": "..."}` (idempotent — re-running it just returns the existing client's id). From there, the client redirects to this worker's `/api/auth/oauth2/authorize`, the visitor authenticates against the `/login` SPA route above (accounts are seeded ahead of time via `worker/bootstrap-admin-user.ts` — there's no sign-up page to fall back to) and grants consent on `/consent`, and the client exchanges the resulting authorization code for tokens at `/api/auth/oauth2/token`. A non-loopback deployment means calling the same route with that deployment's `redirect_uri`. A genuinely new client means adding its name to `CLIENT_NAMES` in `worker/register-oauth-client.ts`.
